Three Clocks, One Body

The latency hierarchy of the CivQuest agent harness Verified against commit d951ea6 · 2026-11-24 Numbers are tagged design budget or not measured

An embodied agent has to react to a hazard in milliseconds and to decide what to build over seconds. A language model cannot do the first, and a reflex loop cannot do the second. CivQuest splits control across three clocks, 20 Hz inside the game engine, 5 Hz in a Go controller, and an asynchronous LLM planner, and constrains how information may cross between them. This page states that partition as testable claims, shows the data path, and marks which numbers are design targets rather than measurements.

  1. A hazard outruns the harness. A reflex that must cross a process boundary is a slower reflex, so survival reflexes execute inside the engine tick and never wait for the controller.
  2. Slow cognition must not hold the controller. Planner output re-enters control asynchronously, and the controller keeps running whether or not it arrives.
  3. The way back in is narrow by design. Planner output reaches control only as a schema-validated directive from a fixed vocabulary. That keeps System 1 deterministic, and it caps what the planner can ask for.

1The problem

CivQuest agents are server-side avatars in a Minecraft world. Each has a body that the game engine simulates at 20 ticks per second, and a mind that lives in a separate Go process. Between them is a gRPC stream. Three requirements pull against each other:

Survive. Projectiles, fall damage and fire act within a tick or two. Act coherently. Walking to a tree, placing blocks and sleeping are multi-second behaviours that must resume correctly after interruption. Think. Dialogue, bartering and choosing where to settle take an LLM seconds, and a local model on shared hardware takes longer under load. No single loop can satisfy all three, so the architecture gives each requirement its own clock and its own failure budget.

2Three clocks, one axis

Figure 1 puts every operation on the same logarithmic time axis. The bars are not equally trustworthy, and the figure says which: ceilings are budgets that the code is designed to meet, and ranges are estimates.One server tick is 50 ms. Telemetry is emitted on every fourth tick, offset per agent by a hash of its UUID, so 5 Hz agents do not all collect frames on the same tick.

Two readings matter. First, the reflex tier sits left of the IPC bar. A reflex that depends on a round trip to Go sits to its right, past 5 ms and potentially past a server tick, which is why reflexes live in AgentEntity.tick(). Second, there is nothing between 20 ms and 500 ms. The harness has no middle tier. Everything slower than the controller is treated as unboundedly slow, and the 30 s request timeout is how that case surfaces (Section 5).

Three mechanisms keep the clocks decoupled. Coalesced slots: SlotQueue keeps one pending intent per type (navigate, attack, use-item, craft, interact), so a controller running faster than the actuator overwrites stale intent instead of queueing it. Receipts: each batch carries a sequence number and the body answers with an IntentReceipt, which is how System 1 learns an action was refused or finished rather than assuming. Snapshot in, directive out: System 2 gets the FactGraph rendered as text, and it can only influence behaviour through a schema-validated directive that System 1 chooses whether to act on.

5Crossing the boundary

The two fast tiers share a tick-and-frame rhythm. The seam to System 2 is where timing stops being predictable, so it is the most constrained part of the design.

Planner to controller: directives

Contemplation returns goals as text and, alongside them, a structured StrategicDirective whose action is one of seven values: GATHER_TIMBER, MINE_STONE, FORAGE_FOOD, CRAFT_SURVIVAL_KIT, BUILD_SHELTER, SCOUT_FRONTIER, SOCIALIZE. If the model omits the field, a deterministic fallback infers one from the goal text. The directive is written into the FactGraph, and System 1 skills act on it through their ordinary preconditions. The planner never emits intents, so a bad or late directive can only change what System 1 prefers, never bypass its guards. The cost is a ceiling: the planner can only ask for things in this list.

Peer speech: who is allowed to call the model

When an agent speaks, every listener within 20 m would otherwise start its own LLM request. Figure 3 shows the gate that prevents it. Every listener records the statement to episodic memory, which costs no tokens. Whether it also replies depends on the message: a direct address or a hazard keyword bypasses the ambient election; otherwise a hash of (speaker, message, listener) elects roughly one listener in four (one in three if the message contains a question mark). Elected replies wait a name-derived 0.25–1.5 s, and each agent keeps a 30 s global cooldown across peers plus a 90 s per-peer cooldown. Hazard alerts bypass the cooldowns.

What the harness lacks is a policy for overload. When the gateway is saturated, requests wait and then fail at the 30 s timeout. There is no priority between a player's message and ambient agent chatter, and no deterministic fallback reply.

The pattern is that the architecture's structure is documented and tested at the unit level, while its timing claims are asserted. Closing that gap is the highest-value change to this page.

7Toward robots

The project's second aim is a harness that could drive an embodied agent outside a game. The latency partition is the part most likely to carry over, so this page tests it against the obvious mapping and lists where it breaks.

HereOn a robotTransfers?
Reflex tier in the tickFirmware or servo-level safety controllerYes. The rule that a reflex acts first and reports afterwards matches common safety-controller practice.
System 1, 5 Hz frameReal-time controller / behaviour tree on the robotMostly. A real controller usually runs faster than 5 Hz and cannot assume a clean frame.
System 2 LLMTask planner or VLM, possibly off-boardYes, and a network hop makes its slowness worse.
TelemetryFrameFused sensor stateNo. Frames here are exact. There is no sensor noise, occlusion, calibration drift or state estimation.
IntentReceiptActuation feedbackPartly. Here the engine knows whether an action finished. A robot may only infer it.
Loopback gRPCRadio, bus or wired linkNo. The 5–20 ms IPC bar would be larger, variable and lossy.

The honest summary is that the partition and the receipt discipline are plausible to carry over, and the perception side does not carry over at all, because a voxel world gives the harness exact ground truth for free.
