Hierarchical State Machine &
Intent Actuation Pipeline

Unconstrained priority cascades produce erratic agent behaviors, race conditions, and illegal state transitions. CivQuest replaces ad-hoc rule scoring with a formal Hierarchical Finite State Machine (HFSM), enforcing strict transition guards, entry/exit queue purging, and inventory-gated ghost intent pruning.

Level 1: Intuitive Mental Model

Sleeping Mid-Combat & Firing Empty Guns

TMLI-15 Framing

Imagine an autonomous robot designed to explore an island. If you program it with a list of independent rules—like "If it's night, go to sleep" and "If a predator attacks, run away"—what happens when a predator attacks at 9:01 PM? Without a structured state machine, the clock rule might override the combat rule, causing the robot to lie down and take a nap while actively being eaten alive.

A formal State Machine acts like an air traffic controller. You cannot transition from Fleeing Combat to Sleeping in Bed unless a strict security checkpoint is cleared (the hostile threats must be dead or out of range, and the agent must be inside an enclosed shelter).

Furthermore, consider "Ghost Intents": if an agent panics and screams "Raise Shield!" fifty times per second across the network, but their backpack contains no shield, the game engine wastes CPU processing empty commands while network buffers fill with garbage. CivQuest validates physical prerequisites before emitting intents, ensuring every packet sent across the wire produces real physical effects.

Level 3: Deep As-Built Implementation

State Structures, Inventory Pruning & Stuck Recovery

TMLI-Pro Systems Engineering

1. The HFSM Go Data Structure (`internal/system1/fsm.go`)

The state machine is implemented as an explicit transition table where state nodes define entry hooks, tick evaluators, and exit cleanup actions:

orchestrator-go/internal/system1/fsm.go 
type StateType string

const (
    StateBootstrap StateType = "BOOTSTRAP"
    StateExplore   StateType = "EXPLORE"
    StateShelter   StateType = "SHELTER"
    StateEmergency StateType = "EMERGENCY"
    StateRest      StateType = "REST"
)

type StateNode struct {
    Type        StateType
    OnEnter     func(ctx *ExecutionContext)
    OnTick      func(ctx *ExecutionContext) error
    OnExit      func(ctx *ExecutionContext)
    Transitions []TransitionRule
}

type TransitionRule struct {
    TargetState StateType
    Guard       func(ctx *ExecutionContext) bool
    Priority    int
}

2. Ghost Intent Elimination & Inventory Pre-flight Guards

Prior to emitting intents across gRPC, `confidence.go` and `evaluator.go` inspect the agent's cached inventory snapshot. If the agent has no shield in their inventory or offhand slot, `RaiseShield` is strictly forced to `false`:

orchestrator-go/internal/system1/confidence.go 
func (e *Evaluator) EvaluateCombatReflexes(ctx *ExecutionContext) *civquestv1.AttackIntent {
    intent := &civquestv1.AttackIntent{
        TargetEntityId: ctx.Threats[0].EntityId,
        Flee:           ctx.SurvivalConfidence < 0.40,
    }

    // Ghost Intent Guard: Only request shield raise if shield is physically held
    if ctx.HasShield {
        intent.RaiseShield = true
    } else {
        intent.RaiseShield = false // Prevent 50+ Hz ghost intent spam
    }

    return intent
}

3. Stuck-State Detection & Fallback Recovery

When an agent is executing a pathing intent in `StateExplore` or `StateShelter`, voxel obstructions or unreachable blocks can cause the avatar to freeze in place. The harness tracks spatial progress over time:

\text{Stuck Condition: } \quad \sum_{i=0}^{N} |\vec{P}_{t} - \vec{P}_{t-1}| < 0.5\text{ blocks} \quad \text{for } N \ge 10\text{ ticks (2.0s)}

Upon detecting a stuck state, the HFSM fires the `OnExit` hook, clears the current Baritone navigation target, emits a small lateral jump intent, and selects a fallback exploration vector offset by $+90^\circ$.
