Relational & Vector
Persistence Engine

Autonomous dynastic agents require durable episodic memory: exact transactional records for economic barter, relationship meters for clan politics, and semantic vector embeddings for associative memory recall. CivQuest embeds a dedicated SQLite database per agent augmented with the sqlite-vec extension.

The Dual-Memory Model: Exact Ledgers vs. Associative Recall

Human memory operates in two very different ways:

  • Exact Relational Memory: "How many iron ingots did I trade to Baker yesterday at noon?" This requires an exact accounting ledger. If the record is fuzzy or estimated, trade disputes and starvation follow.
  • Associative Semantic Memory: "Where was that dark ravine where a creeper ambushed me in the rain last week?" This is not an exact spreadsheet query; it is a conceptual search across sensations, emotions, and landmarks.

CivQuest combines both memory models inside a single, high-performance database file. Standard SQL tables record exact inventory transactions, clan contracts, and reputation points. Simultaneously, the sqlite-vec extension converts sensory experiences and dialogue into mathematical vector coordinates, allowing the agent to recall relevant memories using cosine similarity.

By utilizing SQLite's Write-Ahead Logging (WAL) mode, the agent's fast 5 Hz sensory loop can write updates continuously without ever being blocked when an LLM is reading historical memories in the background.

Embedded Relational & Vector Storage Architecture

Per-agent persistence combines ACID transactional guarantees with low-latency vector nearest-neighbor search, eliminating external database server dependencies.

Persistence & Zero-Daemon Invariants

Zero External Daemons: The persistence tier must not depend on external database services (Postgres, Redis, Milvus). All relational and vector data resides inside a single $XDG_DATA_HOME/civquest/agents/{id}/agent.db file.

WAL Concurrency: Databases must operate in Write-Ahead Logging mode (PRAGMA journal_mode=WAL) to allow non-blocking concurrent reads by background System 2 workers during active 5 Hz System 1 telemetry writes.

Zero-Maintenance Persistence Guarantee

By embedding relational tables and vector nearest-neighbor indices directly inside a single SQLite file, agent state is 100% self-contained, enabling instant backups, atomic graveyard migrations, and sub-millisecond retrieval without external services.

DDL Schemas, WAL PRAGMAs & sqlite-vec Extension

1. Database Initialization & WAL PRAGMAs (internal/db/agent_db.go)

Every agent process initializes its database connection with strict concurrency and performance tuning:

func OpenAgentDB(dbPath string) (*sql.DB, error) { db, err := sql.Open("sqlite3", dbPath+"?_journal_mode=WAL&_synchronous=NORMAL&_busy_timeout=5000") if err != nil { return nil, err } // Load sqlite-vec shared extension library if err := loadSqliteVecExtension(db); err != nil { return nil, fmt.Errorf("failed to load sqlite-vec: %w", err) } db.SetMaxOpenConns(1) // Single writer per process return db, nil }

2. Schema Definition & Virtual Vector Table DDL

The schema establishes the relational backbone and vector virtual table:

CREATE TABLE IF NOT EXISTS episodes ( id INTEGER PRIMARY KEY AUTOINCREMENT, tick INTEGER NOT NULL, summary TEXT NOT NULL, emotion_tag TEXT, location_x REAL, location_y REAL, location_z REAL, created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ); -- sqlite-vec virtual table for 384-dimensional dense embeddings CREATE VIRTUAL TABLE IF NOT EXISTS vec_episodes USING vec0( embedding float[384] distance_metric=cosine );

3. Vector Ingestion & RAG Query Pipeline (internal/db/vector.go)

When an episode is recorded, the embedding is computed and inserted atomically into both the relational table and the virtual vector index:

func (db *AgentDB) QuerySimilarEpisodes(ctx context.Context, queryEmbedding []float32, limit int) ([]Episode, error) { query := ` SELECT e.id, e.tick, e.summary, e.emotion_tag, v.distance FROM vec_episodes v JOIN episodes e ON e.id = v.rowid WHERE v.embedding MATCH ? ORDER BY v.distance ASC LIMIT ?; ` rows, err := db.conn.QueryContext(ctx, query, serializeEmbedding(queryEmbedding), limit) if err != nil { return nil, err } defer rows.Close() return scanEpisodes(rows) }

Footnotes & Conceptual Provenance
  1. Write-Ahead Logging (WAL) and ARIES Recovery: Appending non-blocking mutations to a write-ahead log file allows multiple concurrent readers to query the relational state without acquiring read locks against active single-writer transactions. See: Mohan, C., et al. (1992). ARIES: A Transaction Recovery Method Supporting Fine-Granularity Locking and Partial Rollbacks Using Write-Ahead Logging. ACM Transactions on Database Systems, 17(1), 94–162.
  2. Episodic vs. Semantic Memory in Cognitive Architectures: Endel Tulving's division between episodic memory (temporally organized autobiographical life events) and semantic memory (timeless structural facts and relationships) provides the cognitive blueprint for RAG retrieval over autobiographical logs. See: Tulving, E. (1983). Elements of Episodic Memory. Oxford University Press; Park, J. S., et al. (2023). Generative Agents: Interactive Simulacra of Human Behavior. UIST'23.
