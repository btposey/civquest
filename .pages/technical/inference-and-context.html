Context Assembly Pipelines

While System 1 guarantees physical survival, System 2 drives high-level cognitive life: social barter negotiation, dynastic book chronicles, settlement landmark naming, and spatial architectural blueprints. CivQuest connects to local LLM gateways via strict JSON Schema boundaries and dual-temperature sampling.

Level 1: Intuitive Mental Model

Directing Actors with Strict Stage Scripts

TMLI-15 Framing

Imagine directing an improvisational theatre actor. If you give them complete freedom with no guardrails, they might hallucinate alien spaceships in the middle of a medieval historical play. If you instead hand them an exact template with specific slots—such as "Trade Proposal: Offer X items for Y items"—they can express creative personality without breaking the rules of the world.

Furthermore, different cognitive tasks require different levels of randomness:

  • Structured Tactical Decisions (Low Temperature $\tau = 0.2$): When calculating barter exchange ratios or assembling construction blueprints, we need deterministic, mathematical consistency. Zero hallucinations are tolerated.
  • Narrative Lore & Social Dialogue (High Temperature $\tau = 0.8$): When settlers sit around an evening campfire writing chronicles in Minecraft books or chatting with players, we want rich literary vocabulary, humor, and unique dynastic personalities.

CivQuest enforces this separation by routing structured outputs through strict JSON Schema parsers before any action touches the game engine.

Level 3: Deep As-Built Implementation

Schemas, Minecraft Book Pagination & Fallbacks

1. The Barter Proposal JSON Schema (`internal/system2/types.go`)

When an agent initiates a trade with another settler or player, the LLM must return a validated JSON payload adhering to strict bounds:

orchestrator-go/internal/system2/types.go 
type TradeProposalResponse struct {
    OfferedItem   string  `json:"offered_item"`   // e.g. "minecraft:bread"
    OfferedCount  int32   `json:"offered_count"`  // Must be > 0 and <= HeldInventoryCount
    DemandedItem  string  `json:"demanded_item"`  // e.g. "minecraft:iron_ingot"
    DemandedCount int32   `json:"demanded_count"` // Must be > 0
    DialogueText  string  `json:"dialogue_text"`  // Max 120 chars for chat packet
    FairnessScore float64 `json:"fairness_score"` // Clamped [0.0, 1.0]
}

2. Chronicler Book Pagination Algorithm (`internal/system2/chronicler.go`)

Minecraft writable books (`Items.WRITABLE_BOOK`) enforce strict physical limitations: a maximum of 255 characters per page and up to 100 pages per volume. The Chronicler engine formats generated lore into discrete pages without splitting words across line breaks:

orchestrator-go/internal/system2/chronicler.go 
func PaginateBookContent(rawText string) []string {
    const MaxPageChars = 240 // Safety margin below 255 Minecraft limit
    words := strings.Fields(rawText)
    var pages []string
    var currentPage strings.Builder

    for _, word := range words {
        if currentPage.Len()+len(word)+1 > MaxPageChars {
            pages = append(pages, currentPage.String())
            currentPage.Reset()
        }
        if currentPage.Len() > 0 {
            currentPage.WriteString(" ")
        }
        currentPage.WriteString(word)
    }
    if currentPage.Len() > 0 {
        pages = append(pages, currentPage.String())
    }
    return pages
}

3. Failure Modes & Circuit Breakers

System 2 runs entirely in non-blocking background goroutines. If the local Ollama instance experiences high VRAM pressure or fails to respond within $3000\text{ ms}$, the following circuit-breaker sequence triggers:

  1. The pending request context cancels via `context.WithTimeout`.
  2. System 1 utility AI falls back to deterministic item-value lookup tables (`internal/system1/trade_evaluator.go`).
  3. The agent executes the trade immediately without blocking movement or starving sensory telemetry.
